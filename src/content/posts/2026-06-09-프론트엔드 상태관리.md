React Query를 공부하다가 상태관리 라이브러리들의 역할 차이가 궁금해졌다

---

### 서버 state vs 클라이언트 state

상태관리를 이해하려면 이 둘을 구분하는 게 먼저다

**서버 state** — 서버에서 가져오는 데이터

- 책 목록, 댓글 목록, 유저 정보 등
- API 호출로 가져오고 서버가 원본
- 언제든 바뀔 수 있어서 최신 상태 유지가 중요

**클라이언트 state** — 브라우저에서만 관리하는 데이터

- 장바구니 (결제 전 임시 상태)
- 모달 열림/닫힘
- 폼 입력값
- 서버랑 무관하게 UI에서 관리

---

### useState — 컴포넌트 안에서만

가장 기본. 해당 컴포넌트 안에서만 쓰는 state다

```typescript
const [count, setCount] = useState(0);
```

다른 컴포넌트에 전달하려면 props로 내려줘야 한다

---

### Context API — 하위 컴포넌트 전체에 공유

props로 계속 내려주는 **props drilling** 문제를 해결한다

```
App (state)
 ↓ props → ↓ props → ↓ props
Header → Nav → UserIcon  ← 여기서 필요한데 3단계를 거쳐야 함
```

Context API를 쓰면

```typescript
// Provider로 감싼 범위 안에서
const { member } = useAuth(); // 어디서든 바로 접근
```

`Provider`로 감싼 하위 컴포넌트 어디서든 바로 꺼내 쓸 수 있다

보통 최상위(`App`)에서 감싸면 사실상 전역이랑 같아진다

단점은 state가 바뀌면 하위 컴포넌트 전체가 리렌더링될 수 있다

로그인 상태처럼 **단순하고 자주 안 바뀌는 전역 state**에 적합하다

---

### Redux / Zustand — 복잡한 클라이언트 state

여러 컴포넌트가 동시에 같은 state를 자주 수정하거나, 복잡한 로직이 있을 때 쓴다

**Redux** — 보일러플레이트가 많고 복잡하지만 대규모 프로젝트에서 검증됨

**Zustand** — Redux보다 훨씬 가볍고 단순해서 요즘 신규 프로젝트에서 선호

Vue에서는 **Pinia**가 같은 역할을 한다 (Vuex의 후계자)

```typescript
// Zustand 예시
const useCartStore = create((set) => ({
    items: [],
    addItem: (item) => set((state) => ({ items: [...state.items, item] })),
    removeItem: (id) => set((state) => ({ items: state.items.filter(i => i.id !== id) })),
}));
```

---

### React Query — 서버 state 전용

서버에서 가져오는 데이터를 전역 캐시로 관리한다

`useState + useEffect`로 직접 구현하던 로딩/에러 상태 관리를 추상화하고, 캐싱과 자동 리패칭까지 제공한다

어느 컴포넌트에서든 같은 queryKey로 접근하면 같은 캐시를 바라본다

---

### 역할 분리해서 조합하기

요즘 일반적인 패턴은 역할에 따라 나눠서 쓰는 것이다

| 용도 | 선택 |
|---|---|
| 서버에서 가져오는 데이터 | React Query |
| 단순한 전역 state (로그인 등) | Context API |
| 복잡한 클라이언트 state | Zustand |
| 컴포넌트 내부 state | useState |

실제 흐름으로 보면

```
React Query → 서버에서 상품 목록 가져옴
    ↓
Zustand → 장바구니에 담기 (클라이언트에서 관리)
    ↓
React Query (useMutation) → 결제 시 서버로 전송
```

---

### Redux는 줄어드는 추세

React Query가 서버 state를 담당하면서 Redux가 할 일이 많이 줄었다

예전엔 서버 데이터까지 Redux로 관리했는데, React Query가 그 역할을 가져가면서 Redux는 순수한 클라이언트 state 관리로 축소됐다

보일러플레이트가 많고 학습 곡선이 높아서 요즘 신규 프로젝트에서는 Zustand나 Context API로 대체하는 경우가 많다
