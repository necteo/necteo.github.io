## 시작

프로젝트들을 다시 돌아보면서 문득 궁금해졌다. 브라우저에 주소를 치면 **그 요청이 어디를 거쳐 화면으로 돌아오는거지?** 리버스 프록시, 웹 페이지 렌더링, Axios 호출 같은 걸 따로따로는 알았는데 하나로 이어보려니 정확하게 떠오르는 이미지가 없었다. 그래서 요청 하나를 처음부터 끝까지 따라가며 정리했다. 마지막엔 같은 질문을 React(SPA)에도 던져, **서버가 화면을 그리는 방식(SSR)과 브라우저가 그리는 방식(CSR)이 어떻게 다른지**까지 정리했다.

## 전체 경로

AllMoive 프로젝트를 예로 알아보았다.

```
브라우저
  │  GET https://sist-all-movie.duckdns.org/store/list
  ▼
DuckDNS (도메인 → EC2 IP)
  |
  ▼
Nginx (443, 리버스 프록시)
  │  proxy_pass → localhost:8000
  ▼
Spring Boot (내장 Tomcat, 8000)
  │  DispatcherServlet → Controller → ViewResolver → Jasper(JSP)
  ▼
HTML 생성 → 다시 Nginx → 브라우저
```

크게 **① Nginx 구간**, **② Spring 내부 구간**, **③ 화면 뜬 뒤 Axios 구간** 세 덩어리로 나뉜다.

## ① Nginx — 리버스 프록시

모든 요청은 일단 Nginx(443)로 들어온다. Nginx는 **서버 앞에 서서 요청을 대신 받아 내부로 넘겨주는 중간 서버**다(리버스 프록시). 브라우저는 Nginx하고만 대화한다고 생각하고, 뒤에 Spring Boot가 8000에서 도는 건 모른다.

```nginx
upstream allmovie {
    server localhost:8000;
}
server {
    listen 443 ssl;        # HTTPS 종료
    location / {
        proxy_pass http://allmovie;   # 내부 8000으로 전달
    }
}
```

### 포트 포워딩이랑 헷갈렸던 점

처음엔 "443 → 8000으로 넘기니까 포트 포워딩 아닌가?" 했는데 아니다.

- **포트 포워딩**: L4(패킷). 봉투 안 안 보고 주소·포트만 바꿔 전달.
- **리버스 프록시**: L7(HTTP 이해). 요청을 받아 읽고 새로 연결해 전달.

결정적 차이는 **TLS termination**이다. Nginx가 443에서 **HTTPS를 복호화**해 평문으로 8000에 넘긴다. 포트 포워딩은 암호를 못 푼다(암호화된 바이트를 그냥 통과시킬 뿐). Nginx가 인증서를 들고 복호화까지 하니 이건 리버스 프록시다.

> HTTPS는 DuckDNS(무료 도메인) + Let's Encrypt(무료 인증서) + Nginx(443에서 TLS 종료) 조합으로 적용했다.

## ② Spring 내부 — 요청이 JSP가 되기까지

Nginx가 넘긴 요청은 내장 Tomcat 위의 Spring 앱으로 들어간다.

**1. DispatcherServlet이 받는다.** Spring MVC에서 서블릿은 **이거 하나뿐**이고, 이게 모든 요청을 받아 여러 `@Controller`로 분배한다. (옛날 순수 서블릿 방식 — URL마다 클래스가 컨트롤러 역할 — 과 결정적으로 다른 점)

**2. Controller가 처리하고 뷰 이름을 반환한다.** 파일 경로가 아니라 그냥 문자열이다.

```java
@Controller
@RequestMapping("/store")
public class StoreController {
    @GetMapping("/list")
    public String store_list(Model model) {
        model.addAttribute("main_jsp", "../store/list.jsp");
        return "main/main";   // ← 뷰 '이름'
    }
}
```

**3. ViewResolver가 그 이름에 prefix·suffix를 붙여 물리 경로로 바꾼다.**

```yaml
spring:
  mvc:
    view:
      prefix: /WEB-INF/views/
      suffix: .jsp
# "main/main" → /WEB-INF/views/main/main.jsp
```

**4. 그 JSP로 forward되면 Jasper(Tomcat의 JSP 엔진)가** JSP를 **서블릿으로 컴파일**(첫 호출 1회만, 이후 캐싱)해서 실행한다. 그 결과로 **HTML이 생성**된다.

### 여기서 알게 된 것

- **`.jsp` 파일이 브라우저로 가는 게 아니다.** Jasper가 서버에서 JSP를 *실행*해서 만든 **HTML만** 나간다. 브라우저는 jsp 원본을 절대 못 본다. 이게 서버사이드 렌더링(SSR).
- **`/WEB-INF/` 아래 JSP는 URL로 직접 접근 불가.** 컨트롤러를 통한 forward로만 닿는다. 그래서 뷰를 거기 둔다(보안).
- **JSP를 쓰려면 Jasper(서블릿 컨테이너)가 필요**해서, fat-JAR가 아니라 **WAR로 패키징**했다. 배포 파이프라인의 "War 파일 생성"이 이것과 연결된다.

## ③ 화면이 뜬 뒤 — Axios로 호출

JSP가 내려준 HTML 안에는 **Vue.js(CDN)**가 들어있다. 페이지가 뜨면 브라우저에서 Vue가 돌면서 필요한 데이터를 **Axios로 다시 요청**한다.

```js
// 결제 준비 요청
const { data } = await api.post('/payment/prepare', { ... })
```

여기서 중요한 건, **이 API 요청도 결국 브라우저에서 나가는 요청**이라는 거다. 그러니 페이지 받을 때랑 똑같이 `duckdns 도메인 → Nginx → Spring Boot`를 탄다.

> **규칙**: 브라우저 ↔ 서버 = 무조건 Nginx 경유 (HTML이든 JSON이든).
> 서버 ↔ DB, 서버 내부 forward = Nginx 안 거침.

즉 AllMovie는 **JSP(SSR)로 뼈대를 내려주고, 그 위에서 Vue(CSR)가 동적 데이터를 채우는** 혼합 구조다.

## ④ baseURL은 상황에 따라 설정

API 호출 코드를 보면 주소가 상대경로(`/payment/prepare`)다. Axios 인스턴스에 **baseURL을 안 줬기 때문**이다.

```js
const api = axios.create({ timeout: 50000 }); // baseURL 없음
```

baseURL이 없으면 요청은 **페이지가 로드된 origin**으로 간다.

- 로컬: `http://localhost:8000/payment/prepare`
- 배포: `https://sist-all-movie.duckdns.org/payment/prepare`

환경에 따라 알아서 맞는 주소로 가니, 코드를 안 고쳐도 로컬·배포가 다 된다. 이게 가능한 건 **JSP+Vue를 Spring Boot가 직접 서빙**해서 프론트와 백엔드가 **같은 origin**이기 때문이다.

반대로 개인 프로젝트 BookTalk은 React를 별도 서버로 분리해서 origin이 다르다. 그래서 거긴 baseURL을 박아야 한다.

```ts
// BookTalk — 프론트·백 분리 → baseURL 필수
const apiClient = axios.create({
	baseURL: 'http://localhost:8080',
	withCredentials: true,
});
```

> 정리하면 **프론트를 백엔드가 같이 서빙하면(AllMovie) 상대경로로 생략, 분리돼 있으면(BookTalk) baseURL 설정** 이 기준이다.

## ⑤ React(SPA)는 어떻게 다른가 — CSR

AllMovie(JSP)는 **서버가 화면을 만들어서 준다**(SSR). 개인 프로젝트 BookTalk의 React는 정반대다(CSR).

React를 빌드하면(`react-scripts build`) `build/` 폴더에 **정적 파일**이 나온다.

- `index.html` — 거의 빈 껍데기 (`<div id="root"></div>`가 전부)
- `static/js/*.js` — 컴파일된 React 앱(번들)

이걸 **정적 파일 서버**(개발 땐 `react-scripts start`의 dev server, 배포 땐 Nginx·Netlify·Vercel 등)가 그냥 내려준다. **여기엔 ViewResolver도 Jasper도 없다.** 서버는 렌더링을 안 하고 파일만 전송한다.

화면은 **브라우저가 JS를 실행해서 그린다.**

```
1. URL 입력 → DNS가 도메인을 프론트 서버 IP로 변환
2. 브라우저 → 프론트 서버 → index.html + JS 번들 받음
3. 브라우저가 index.html 파싱 → JS 번들 실행 (React 부팅)
4. React Router가 현재 URL 경로·파라미터를 읽어 → 맞는 컴포넌트 렌더 시작
5. 그 컴포넌트가 Axios로 백엔드 API 호출 → JSON 받음
6. 받은 데이터로 화면 완성
```

헷갈리기 쉬운 점:

- **프론트 서버는 조립을 안 한다.** Axios 호출도 화면 완성도 **전부 브라우저**가 한다. 프론트 서버는 파일 배달부다.
- **`index.html`은 맨 처음에**(빈 껍데기로) 나간다. 완성 후가 아니다.
- **경로별 페이지가 서버에 없다.** `/board`든 `/login`이든 **같은 index.html 하나**를 주고, 어떤 화면을 그릴지는 브라우저의 React Router가 정한다(클라이언트사이드 라우팅).
- 백엔드는 **JSON 데이터만** 준다. JSP가 없으니 보통 **JAR**로 실행(`java -jar`)한다. (WAR는 AllMovie가 JSP·Jasper 때문에 쓴 것)

### SSR vs CSR 정리

|                | SSR (JSP / AllMovie)      | CSR (React / BookTalk)         |
| -------------- | ------------------------- | ------------------------------ |
| 경로 해석      | 서버 (DispatcherServlet)  | 브라우저 (React Router)        |
| 화면 조립      | 서버 (Jasper가 HTML 완성) | 브라우저 (JS가 그림)           |
| 서버가 주는 것 | 완성된 HTML               | index.html + JS, 데이터는 따로 |
| 프론트·백      | 한 서버(Spring)           | 분리 (프론트 서버 + API 서버)  |
| 패키징         | WAR (JSP·Jasper 필요)     | JAR (REST만)                   |

## 마무리

요청 하나를 끝까지 따라가보니 따로 알던 개념들이 하나로 이어졌다.

> 브라우저 → (DuckDNS) → **Nginx(리버스 프록시·TLS 종료)** → **DispatcherServlet → Controller → ViewResolver → Jasper** → HTML → 다시 Nginx → 브라우저. 그리고 그 위에서 **Vue가 Axios로 같은 경로를 다시** 탄다.

JSP든 JSON이든 경로는 똑같고, 차이는 _Spring이 응답을 어떻게 만드느냐(JSP 렌더 vs JSON 직렬화)_ 뿐이라는 게 가장 크게 남는다.

그리고 한 발 더 나가면, **화면을 누가 그리느냐**(서버=>SSR, 브라우저=>CSR)가 JSP와 React를 가르는 핵심이라는 것도 함께 정리됐다.
