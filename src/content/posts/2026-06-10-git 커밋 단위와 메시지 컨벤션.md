### 커밋 단위 — 되돌릴 수 있는 최소 단위

커밋 단위의 기준은 **하나의 논리적으로 완결된 변경**이다. 기능 하나보다 보통 더 잘게 나눈다

핵심 원칙은 **이 커밋만 revert해도 다른 게 안 망가지면 잘 나눈 것**이다

기능 하나가 크면 그 안에서도 쪼갠다. 예를 들어

```
❌ "JWT 인증 개선" (한 덩어리)

✅ 이렇게:
- fix: refresh 401 무한 루프 차단
- refactor: member/me를 인증 필요로 변경
- refactor: 도달 불가한 204 분기 제거
```

각 커밋이 독립적으로 의미가 있고, 하나만 봐도 뭘 왜 바꿨는지 명확하다

---

### 좋은 커밋 단위의 기준

- **한 가지 일만** — 버그 수정 + 리팩토링 + 기능추가를 한 커밋에 섞지 않는다
- **빌드가 깨지지 않음** — 각 커밋 시점에 컴파일/테스트가 통과해야 한다
- **한 줄로 설명 가능** — 메시지에 "그리고", "또"가 들어가면 쪼갤 신호다

---

### 자주 커밋하되, push는 정돈해서

**자주 커밋**이 좋다. 다만 정확히는 **로컬은 자주, 공유(push)는 정돈해서**다

자주 커밋하면 좋은 이유

- 되돌리기 쉬움 — 망가지면 마지막 정상 커밋으로 복구
- 작업 단위가 명확해짐
- push해두면 백업
- diff가 작아 리뷰/디버깅 쉬움 (`git bisect`로 버그 들어온 커밋 추적도 가능)

현실적으로는 작업 중엔 `wip`(work in progress) 커밋을 막 쌓다가, **PR/push 전에 정리**하는 경우가 많다

```
작업 중:  wip → wip → 버그 고침 ...   (로컬에서 부담 없이)
push 전:  rebase로 깔끔한 커밋 몇 개로 정리
```

| 상황          | 권장                               |
| ------------- | ---------------------------------- |
| 로컬 작업     | 자주, 부담 없이                    |
| push/PR       | 의미 단위로 정돈해서               |
| 개인 프로젝트 | 나중에 봐도 이해되는 수준이면 충분 |

---

### 커밋 메시지 컨벤션

많이 쓰는 타입

```
feat: 새 기능
fix: 버그 수정
refactor: 동작 변경 없는 구조 개선
docs: 문서
style: 포맷팅
test: 테스트
chore: 빌드/설정
```

제목은 50자 이내 한 줄이면 충분하고, 본문은 필요할 때만 붙인다

**`feat`은 새로 추가된 기능에만** 쓴다. 이게 헷갈리기 쉬운데, 이미 있던 기능을 고친 거면 `fix`/`refactor`다

실제로 내 프로젝트 변경을 정리할 때, 도서·댓글·챗봇은 전부 예전에 커밋된 기능이었다 (`git log`에 `book`, `comment`, `chat`이 이미 있었다). diff를 보니

- 도서/챗봇: API 경로를 `/api/*`로 통일 → **refactor**
- 댓글: id 타입 `String`→`Long`, PK 자동생성 → **fix**

`feat`은 하나도 없었다. "기능을 새로 만들었나, 기존 걸 고쳤나"로 구분하면 된다

---

### 예전 방식과 비교 — 왜 컨벤션이 나은가

전에 내가 쓰던 커밋 메시지는 이런 식이었다

```
oauth
book
css, mysql
add book board etc
comment
```

규칙은 대충 "새로 추가하면 `add`, 고치면 건드린 영역 이름(oauth, book...)"이었다. 파일 상태(추가 A / 수정 M)에 가깝게 분류한 셈이다

이 방식의 문제는

**1. 무엇을 했는지가 빠진다**

`oauth`, `book`은 어디를 건드렸는지만 말하지 무엇을 했는지는 없다. 기능을 추가한 건지, 버그를 고친 건지, 구조만 바꾼 건지 메시지만 봐선 모른다

`fix: 토큰 만료 시 401 처리`는 영역(토큰) + 행동(만료 처리) + 성격(fix)이 한눈에 들어온다

**2. 파일 상태는 git이 이미 안다**

"추가=add, 수정=M" 식 분류는 git이 diff에 이미 기록하는 정보다 (A/M/D). 메시지가 그걸 또 적는 건 중복이고, 정작 중요한 **무슨 변경이고 왜 했나**는 빠진다

특히 수정(M)은 버그 수정인지 리팩토링인지 기능 변경인지 구분이 안 된다. 그 구분이 사실 제일 알고 싶은 정보인데도

**3. 검색이 안 된다**

타입을 달면 `git log --grep="^fix"`로 버그 수정만 모아볼 수 있다. 영역 이름만으론 변경 성격으로 못 거른다

**4. `etc`가 나온다**

`add book board etc` 같은 메시지는 여러 변경을 한 커밋에 몰아넣었다는 신호다. 타입 컨벤션은 "한 커밋 한 가지"를 자연스럽게 유도해서 이런 뭉뚱그림을 막는다

정리하면 — 예전 방식은 **파일이 어떻게 바뀌었나**를 적었고, 컨벤션은 **변경이 무엇이고 왜 했나**를 적는다. git이 이미 아는 걸 반복하지 말고, 모르는 걸 채우는 게 메시지의 역할이다

### `rebase`로 커밋 정리

여러 커밋을 1개로 합치는 걸 **squash**라고 한다. `rebase -i`의 한 기능이다

```bash
git rebase -i HEAD~3
```

편집기에서 `pick`을 바꾸면 커밋을 조작할 수 있다

| 명령           | 의미                           |
| -------------- | ------------------------------ |
| `pick`         | 그대로 둠                      |
| `squash` (`s`) | 앞 커밋에 합침 (메시지도 합침) |
| `fixup` (`f`)  | 앞 커밋에 합치되 메시지는 버림 |
| `reword` (`r`) | 메시지만 수정                  |
| `edit` (`e`)   | 내용 수정                      |
| `drop` (`d`)   | 삭제                           |

**주의 — rebase는 히스토리를 다시 쓴다** (커밋 해시가 바뀜)

- 아직 push 안 한 로컬 커밋 → 자유롭게 OK
- 이미 push해서 공유된 커밋 → `push --force` 필요 → 협업 중이면 위험

그래서 **로컬에서 정리하고 push가 안전**하다

> 헷갈리기 쉬운 것: `squash`(rebase -i 안의 동작)와 `merge --squash`(브랜치 머지 시 커밋들을 1개로 합쳐 가져오기, PR의 "Squash and merge")는 다르다

---

### `push` 타이밍

`push`는 **구현 + 수정 + 리팩토링까지 다 돼서 동작하는 단위**일 때 하는 느낌이다

|      | 로컬 커밋      | push                  |
| ---- | -------------- | --------------------- |
| 성격 | 내 작업 저장   | 공유 / 백업           |
| 상태 | wip, 중간도 OK | 정돈된, 동작하는 상태 |
| 빈도 | 자주           | 한 묶음 끝났을 때     |

예외로 **본인 기능 브랜치**엔 백업 목적으로 미완성도 push하기도 한다. 다만 공유 브랜치(main, develop)엔 동작하는 완결 상태만 올린다

### 블로그 기록 vs git 히스토리

작업을 블로그에 기록하니 git 커밋을 미뤄도 되지 않나 싶었는데, 둘은 역할이 다르다

|                  | 블로그          | git 커밋                 |
| ---------------- | --------------- | ------------------------ |
| 목적             | 학습 기록, 회고 | 코드 변경 추적, 되돌리기 |
| 단위             | 주제/개념       | 코드 변경 단위           |
| 되돌리기         | 불가            | 가능                     |
| 언제 깨졌나 추적 | 불가            | 가능 (bisect, diff)      |

블로그는 "무엇을 배웠나", git은 "코드가 어떻게 바뀌었나"를 남긴다. 블로그가 있어도 git의 실용적 이점(복구, 추적, diff)은 대체되지 않는다

덧붙여 GitHub 커밋 히스토리는 면접에서 보기도 하니, 꾸준히 의미 단위로 커밋하는 것 자체가 기록 + 어필이 된다

---

### 정리

- 커밋 => 되돌릴 수 있는 최소 단위, 한 가지 일만
- 로컬은 자주, `push`는 정돈해서
- `feat`은 새 기능에만 / 기존 기능 수정은 `fix`/`refactor`
- `rebase squash`로 합치되, `push` 전에만
- 블로그와 git은 역할이 다르다
