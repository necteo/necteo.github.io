소셜 로그인을 구현하면서 전체 흐름을 한번 정리해두고 싶었다

JWT는 HttpOnly 쿠키로 관리하고

`SuccessHandler`에서 쿠키를 직접 설정하는 방식으로 구현했다

---

### 1. 로그인 버튼 클릭

```ts
window.location.href = `http://localhost:8080/oauth2/authorization/${provider}`;
```

`axios`가 아니라 `window.location.href`로 브라우저가 직접 이동한다

OAuth2 흐름 자체가 브라우저 리다이렉트 기반이라 이렇게 해야 한다

---

### 2. Spring Security가 소셜 로그인 페이지로 연결

`/oauth2/authorization/google`을 받으면 Spring Security가

CSRF 방지용 `state` 값을 세션에 저장하고 (이때 JSESSIONID 발급됨)

구글 로그인 페이지로 리다이렉트한다

---

### 3. 소셜 서버에서 로그인

사용자가 구글/카카오/네이버에서 로그인하고 동의하면

소셜 서버가 백엔드의 `/login/oauth2/code/google`로 `code`와 `state`를 보낸다

---

### 4. 회원 저장/업데이트 (CustomOAuth2UserService)

받은 `code`로 소셜 서버에서 사용자 정보를 가져온다

provider + providerId로 기존 회원을 찾아 업데이트하거나 없으면 새로 저장한다

```java
return memberRepository
    .findByProviderAndProviderId(provider, info.getProviderId())
    .map(m -> m.update(info.getName(), info.getPicture(), info.getEmail()))
    .orElseGet(() -> handleNewUser(info, provider));
```

소셜마다 응답 구조가 달라서 provider별로 파싱 클래스를 따로 만들었다

카카오는 중첩 구조고 네이버는 `response` 키 안에 데이터가 있다

---

### 5. JWT 발급 및 쿠키 설정 (OAuth2AuthenticationSuccessHandler)

`SuccessHandler`에서 JWT를 발급하고 HttpOnly 쿠키에 직접 설정한다

```java
String accessToken  = jwtTokenProvider.createAccessToken(subject, role);
String refreshToken = jwtTokenProvider.createRefreshToken(subject);

cookieUtil.addAccessTokenCookie(response, accessToken);
cookieUtil.addRefreshTokenCookie(response, refreshToken);

// 이메일이 없는 소셜 계정이면 추가 정보 입력 페이지로 보낸다
String targetUrl = member.getEmail() == null
        ? redirectUri + "/additional-info"
        : redirectUri + "/";
getRedirectStrategy().sendRedirect(request, response, targetUrl);
```

`ResponseCookie`를 사용하면 `Set-Cookie` 헤더가 정상적으로 동작한다

| 쿠키 | 만료 | path |
|------|------|------|
| access_token | 15분 | `/` |
| refresh_token | 7일 | `/api/auth` |

---

### 6. 프론트에서 로그인 상태 반영 (AuthContext)

React가 마운트되면 `/api/member/me`를 호출해 로그인 상태를 확인한다

비로그인이면 `204 No Content`, 로그인이면 회원 정보를 반환한다

```ts
const fetchMember = async () => {
    const { status, data } = await apiClient.get('/api/member/me');
    setMember(status === 204 ? null : data);
};
```

이후 모든 API 요청은 브라우저가 쿠키를 자동으로 포함해서 보낸다

`access_token`이 만료되면 인터셉터가 자동으로 `/api/auth/refresh`를 호출해서 재발급한다

```ts
apiClient.interceptors.response.use(
  (response) => response,
  async (error) => {
    const originalRequest = error.config;

    if (error.response?.status === 401 && !originalRequest._retry) {
      // /api/member/me는 재시도 제외 — 비로그인 상태 확인용이므로
      if (originalRequest.url === '/api/member/me') {
        return Promise.reject(error);
      }
      originalRequest._retry = true; // 무한루프 방지

      try {
        await apiClient.post('/api/auth/refresh');
        return apiClient(originalRequest);
      } catch (refreshError) {
        // Refresh Token도 만료 — 로그인 페이지로 이동
        window.location.href = '/login';
        return Promise.reject(refreshError);
      }
    }

    return Promise.reject(error);
  }
);
```

---

### 마무리

처음에는 `SuccessHandler`에서 `response.addHeader`로 쿠키를 심으려 했는데 무시됐다

URL 파라미터로 토큰을 넘기는 방식으로 우회했다가

`ResponseCookie` + `response.addHeader(HttpHeaders.SET_COOKIE, ...)`로 변경하니

`SuccessHandler`에서도 쿠키 설정이 정상 동작했다

URL에 토큰이 노출되지 않아 보안상으로도 더 안전한 방식이다
