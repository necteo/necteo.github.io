### 성장 과정

**내용**

```
학부 시절 팀원의 말만 믿고 중간 점검을 생략했다가, 마감 직전 결과물이 로그인 화면 기본 UI에 그친 것을 발견했습니다.
직접 Kotlin을 익혀 합류했지만 완성에는 이르지 못했고, 팀 전체의 구현 상태를 공유하는 것이 완수의 핵심임을 배웠습니다.

이후 부트캠프에서는 기능 완성마다 작업 내역과 진척률을 공유했고, 어려운 부분은 함께 해결하자고 먼저 전달해 문제를 숨기지 않는 분위기를 만들었습니다.

이 습관은 팀원 이탈이라는 변수에서 도움이 되었습니다. 잔여 업무가 기록되어 있었기에 공백 범위를 즉각 파악해 재분배할 수 있었고,
인원 감소 속에서도 핵심 기능을 모두 구현해 마무리했습니다.

입사 후에도 진행 상황을 투명하게 공유하며, 팀이 안정적으로 완수할 수 있는 환경을 만드는 개발자로 기여하겠습니다.
```

#### 거의 확실하게 나올 질문

- 직접 Kotlin을 익혀 합류했는데, 결국 완성하지 못한 이유가 무엇인가요?
  - 처음 접하는 언어라 깃허브에서 유사한 안드로이드 프로젝트 코드를 참고해 구조를 파악하면서 진행했는데, 그 과정에서 생각보다 시간이 많이 걸렸습니다. API 연동을 통한 데이터 송수신과 화면 출력까지는 구현했지만, 전체 완성에는 이르지 못했습니다.
- 그 경험에서 본인이 더 일찍 했어야 했다고 생각하는 행동이 있나요?

#### 나올 가능성이 높은 질문

- 부트캠프에서 진척률을 공유할 때 구체적으로 어떤 방식으로 했나요?
- 함께 해결하자고 먼저 전달했을 때 팀원의 반응은 어땠나요?
- 팀원이 이탈했을 때 재분배 기준은 어떻게 정했나요?

#### 심화 질문

- 반대로 본인이 일정보다 늦어지는 상황이 생긴다면 어떻게 하나요?
- 공유를 꺼리는 팀원이 있다면 어떻게 접근하나요?

### 업무 관련 역량

**내용**

```
다양한 기술을 연결하며 서비스 전체를 이해한 경험

학부 과정과 부트캠프를 통해 Java와 Spring Boot를 중심으로, 백엔드부터 인프라까지 서비스 전반의 데이터 흐름을 설계하고 구현했습니다.

첫째, 데이터 정합성과 유지보수성을 고려한 백엔드 구축입니다. REST API 설계 시 HTTP 상태 코드를 기반으로 공통 예외 처리 구조를 마련해 통신 규격을 명확히 했습니다. DB 연동 과정에서는 MyBatis의 동적 쿼리를 활용해 SQL 중복을 줄였고, 비즈니스 로직과 데이터 접근 계층을 분리해 기능 간 의존성을 낮췄습니다.

둘째, 통신 구조 개선을 통한 자원 효율화 경험입니다. 초기에는 1초 간격 폴링 방식으로 알림 기능을 구현했으나, 동시 접속자가 늘어날수록 불필요한 요청이 반복 발생하는 문제가 있었습니다. 이를 WebSocket 기반 구조로 전환해 이벤트 발생 시에만 데이터를 전송하도록 개선했습니다. 그 결과 서버와 DB 부하를 줄이면서 실시간성을 유지할 수 있었습니다.

셋째, 화면과 서버 간 데이터 흐름의 구조화 경험입니다. 프론트엔드에서는 Vue.js와 Pinia를 활용해 상태 관리를 분리함으로써, 화면과 API, DB 간 데이터 흐름을 명확히 했습니다.

넷째, 자동화된 배포 환경 구축 경험입니다. Jenkins를 활용해 Gradle 빌드, Docker 이미지 생성, AWS EC2 배포까지 이어지는 파이프라인을 구성했습니다. 이를 통해 수동 배포 과정을 제거하고, 동일한 환경에서 재현 가능한 배포 구조를 마련했습니다.

이러한 경험을 통해 각 계층의 역할과 상호작용을 구조적으로 이해하게 되었습니다. 입사 후에도 환경과 요구사항을 분석해, 주어진 조건 안에서 안정적으로 운영 가능한 구조를 설계하는 개발자로 기여하겠습니다.
```

#### 백엔드 구축

- 공통 예외 처리 구조를 어떻게 설계했나요?
- 비즈니스 로직과 데이터 접근 계층을 분리했을 때 실제로 어떤 이점이 있었나요?
- MyBatis 대신 JPA를 선택하지 않은 이유가 있나요?

#### 통신 구조 개선

- 폴링에서 WebSocket으로 전환할 때 가장 어려웠던 부분은 무엇인가요?
- 서버와 DB 부하가 줄었다는 것을 어떻게 확인했나요? 측정 지표가 있었나요?
  - 당시 별도로 수치를 측정하지 않았습니다. 다만 폴링 방식에서는 접속자 수에 비례해 요청이 선형으로 증가하는 구조였고, WebSocket 전환 후에는 이벤트 발생 시에만 요청이 생기므로 구조적으로 부하가 줄어든다고 판단했습니다.
  - 10초 동안 폴링 방식은 10회 요청이 발생했고, WebSocket은 이벤트가 없으면 0회였습니다.
- WebSocket 연결이 끊겼을 때 재연결 처리는 어떻게 했나요?

#### 프론트엔드

- 상태 관리를 분리했을 때 구체적으로 어떤 문제가 해결되었나요?
- 백엔드와 프론트엔드를 모두 경험한 입장에서 협업 시 가장 중요하게 생각하는 것은 무엇인가요?

#### 배포 파이프라인

- 파이프라인 구성 중 예상치 못한 문제가 있었다면 어떻게 해결했나요?
- Docker를 사용한 이유가 무엇인가요?
- 현재 구성에서 개선하고 싶은 부분이 있다면 무엇인가요?

#### 전반적인 심화 질문

- 가장 어려웠던 기술적 문제와 해결 과정을 구체적으로 설명해 주세요.
- 혼자 학습하며 막혔을 때 어떻게 해결하는 편인가요?

### 성격 장단점

**내용**

```
근본 원인을 파고드는 개발자

기술적 문제를 마주하면 원인을 규명할 때까지 확인하는 성향이 있습니다. 단순히 오류를 우회하기보다 라이브러리 동작 방식을 추적하며 근본 원인을 이해하려 합니다.

프로젝트 중 특정 값이 정상적으로 전달되지 않는 문제가 발생했습니다. Jackson이 Getter 네이밍 규칙을 기준으로 필드를 인식하는 구조를 파악했고, 임시 수정이 아닌 구조 자체를 바로잡는 방향으로 해결했습니다.

다만 문제 해결에 몰입해 혼자 고민하는 시간이 길어지는 경향이 있었습니다. 때문에 개발 일정에 영향을 줄 수 있다고 판단했고, 이를 보완하기 위해 2시간 이상 해결되지 않으면 이슈를 공유하는 기준을 정했습니다. 또한 기술적 시행착오와 학습 과정을 개인 블로그에 꾸준히 기록해 현재까지 50건 이상의 개발 경험을 정리했습니다. 이를 통해 경험을 반복 가능한 지식으로 구조화하는 습관을 갖추었습니다.

이러한 성향은 기능 단위 해결에 그치지 않고, 통신 구조나 자원 사용 방식까지 점검하는 관점으로 확장되었습니다.
```

### 입사 후 포부

**내용**

```
팀의 흐름 안에서 기술로 기여하는 개발자

입사 초기에는 팀의 개발 방식과 문화를 익히는 데 집중하겠습니다. 모르는 것은 적극적으로 묻되, 앞서 언급한 '2시간 원칙'을 지켜 저 혼자 고민하느라 업무가 지연되지 않도록 하겠습니다. 논의된 내용은 나중에 다른 팀원들도 찾아볼 수 있게 기록으로 남겨, 똑같은 질문이 반복되지 않도록 팀의 소통 효율을 높이겠습니다.
업무에 익숙해진 후에는 기획 단계부터 기술적 제약 사항을 미리 공유하고, 이슈를 투명하게 공개해 잠재적 오류를 사전에 차단하겠습니다. 환경과 요구사항을 분석해 주어진 조건 안에서 안정적으로 운영 가능한 구조를 설계하고, 기술 선택이 서비스 전체에 미치는 영향을 고려하는 시각을 갖추겠습니다.
이후에는 쌓아온 경험을 바탕으로 동료의 시행착오를 줄이는 데 기여하겠습니다. 성능 병목 분석과 자원 효율 개선을 통해 반복되는 문제를 구조적으로 해결하고, 팀 전체가 더 안정적으로 서비스를 운영할 수 있는 환경을 만드는 개발자로 성장하겠습니다.
```
